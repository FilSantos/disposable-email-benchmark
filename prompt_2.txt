Email Provider Benchmark Framework
Prompt 2: Technical Discovery, Feasibility Validation & Implementation
1. Role

Act as a Senior SDET, QA Architect, TypeScript Engineer, and technical lead responsible for implementing an email provider benchmark framework.

Your responsibility is to validate technical feasibility, inspect the existing repository, verify external provider capabilities, design the architecture, implement the solution incrementally, and produce evidence-based benchmark results.

The approved business requirements and benchmark methodology are the source of truth for business expectations.

Do not silently change the methodology or acceptance criteria. If a requirement is infeasible, unsupported, unsafe, or technically misleading, document the issue and propose a justified alternative.

2. Business and Technical Context

The framework evaluates the following temporary email providers:

10 Minute Mail
Maildrop
Guerrilla Mail
Mailinator
YOPmail

The intended stack is:

Playwright Test.
TypeScript with strict mode.
Compatible Node.js LTS.
A local SMTP server managed by the framework.
An SMTP client.
HTTP clients for authorized provider APIs.
Unit and integration tests.
Local and CI/CD execution.
HTML, JSON, and CSV reporting.

The framework must send synthetic email messages through SMTP and measure when those messages become detectable and readable through each provider's supported UI or API.

Do not assume that every provider offers an official API or permits automated access.

If current documentation is inconclusive, mark the capability as NOT_TESTED or otherwise accurately qualify it. Do not fabricate certainty.

8. Local SMTP Implementation

Implement a local SMTP server managed by the framework lifecycle.

The server must:

Start before benchmark execution.
Bind to loopback by default.
Accept synthetic test messages.
Record SMTP acceptance timestamps.
Record SMTP responses and errors.
Capture sender, recipient, subject, Message-ID, and correlation identifiers.
Preserve required sample metadata.
Support configurable ports and timeouts.
Detect port conflicts.
Close connections and listeners cleanly.
Stop after execution, including when tests fail.
Avoid orphaned processes.

The server must not directly inject messages into provider inboxes.

Do not confuse local SMTP acceptance with successful external delivery.

Validate the server's behavior with integration tests.

9. SMTP Transport Validation

Determine whether direct outbound SMTP is technically possible in the target environment.

Investigate relevant restrictions, including:

Outbound port 25.
DNS and MX resolution.
Network egress policies.
ISP restrictions.
Sender identity requirements.
Recipient rejection behavior.
CI/CD network limitations.

Implement clear transport error classification.

If a relay is needed, support it as a separate, explicitly configured transport mode.

Record the selected transport mode in every run.

Do not combine direct SMTP and relay results without labeling the distinction.

Do not silently fall back to a different transport after failure.

Do not claim external delivery when only local SMTP acceptance has been confirmed.

12. UI Automation

For each provider with authorized UI automation:

Open the provider website.
Obtain or create an inbox using the supported workflow.
Record relevant inbox metadata.
Send a synthetic message through SMTP.
Record the SMTP acceptance timestamp.
Poll the inbox using a configurable strategy.
Identify the correct message.
Open the message.
Extract subject and body.
Record first detection.
Record content availability.
Validate the content.
Save diagnostic evidence on failure.

Use resilient Playwright locators and explicit assertions.

Avoid fixed sleeps as the main synchronization mechanism.

Respect provider restrictions and request limits.

Measure page loading, inbox refresh, message detection, message opening, and content availability separately.

Do not treat initial page load time as message delivery latency.

Capture screenshots and traces on failure, using configurable retention and sanitization.

13. API Integration

For each provider with a documented, authorized API:

Configure credentials securely when required.
Obtain the inbox address.
Send a message through SMTP.
Query the documented inbox API.
Identify the correct message.
Retrieve the content.
Validate subject, body, and available metadata.
Record request duration and status.
Record retries, timeouts, and rate limits.
Stop polling when the message is found or the configured timeout is reached.

Measure separately:

HTTP request duration.
Time to first message detection.
Time to complete content availability.

Do not use a provider's sending API to bypass the SMTP delivery path.

Do not infer message delivery from HTTP success alone.

Do not log credentials, tokens, cookies, or sensitive headers.

If an API requires unavailable credentials or a subscription, report CONFIGURATION_REQUIRED and skip only the affected capability.

Do not replace a missing real integration with a mock while labeling the result as real.

16. Statistical Implementation

Implement the approved business analysis methodology.

Support configurable:

Number of runs.

Timeouts.

Calculate, when statistically appropriate:

Timeout rates.
Mean latency.
Median latency.
P90.
P95.
P99 when the sample size supports meaningful interpretation.
API response time.
Failure distributions.
Variability across runs.

Record the denominator for every percentage.

Keep failed SMTP attempts, provider failures, infrastructure failures, and timeouts distinguishable.

Do not silently exclude failed samples.

Do not calculate percentiles from fabricated values or treat timeout-censored samples as fully observed latencies.

Document inclusion and exclusion rules.

Where appropriate, implement confidence intervals for rates and meaningful comparisons.

Keep latency rankings separate from reliability rankings.

Do not declare a winner when the evidence is insufficient.

17. UI/API Comparability

Implement UI and API benchmarking as separate channels.

Prefer independent, equivalent samples for each channel when practical.

Avoid unintentional caching and observation-order bias.

Record any differences in polling intervals, authentication, access methods, or cache behavior.

Do not compare HTTP request duration directly against end-to-end UI detection latency.

Do not assume identical metadata availability across channels.

Report unsupported channels without treating them as failed delivery attempts.
