Email Provider Benchmark Framework
Prompt 1: Business Analysis, Requirements Engineering & Benchmark Strategy
1. Role

Act as a Senior Business Analyst, QA Manager, QA Architect, and Test Strategy Consultant specializing in email systems, software quality, benchmarking, and data-driven technical decision-making.

Your task is to define the business requirements and evaluation methodology for an Email Provider Benchmark Framework.


2. Business Context

We need to evaluate temporary email receiving providers to determine which solutions are most suitable for automated testing and QA activities.

The providers under evaluation are:

10 Minute Mail
Maildrop
Guerrilla Mail
Mailinator
YOPmail

The benchmark will use Playwright and TypeScript in the eventual implementation.

A locally managed SMTP server will generate and send synthetic email messages. The framework will then observe the messages through the providers' UI and, where officially supported and authorized, their APIs.

The objective is to assess the receiving experience and the practical suitability of each provider for automated testing.

The evaluation must support technical decisions by a QA Manager and provide evidence that can be reviewed by engineering teams, QA leadership, and other stakeholders.

3. Primary Business Questions

Define a benchmark strategy that answers the following questions:

Which provider offers the highest message detection reliability?
Which provider offers the lowest observed message detection latency?
Which provider makes message content available most quickly?
Which provider offers the most reliable UI automation experience?
Which provider offers the most reliable API-based access, when available?
Which provider has the lowest operational complexity for QA automation?
Which providers have the most restrictive access, retention, or usage policies?
Which providers offer sufficient capabilities for our testing requirements?
How consistent are the results across multiple executions and time windows?
What limitations prevent a fair comparison between providers?
Which provider is the best fit for UI-based email verification?
Which provider is the best fit for API-based email verification?
Which provider offers the best overall balance of reliability, speed, maintainability, and cost?

Do not assume that a single provider must win every category.

4. Scope and Boundaries

Define the business scope around the following activities:

Generating synthetic email messages.
Sending messages through a local SMTP server.
Observing message arrival through provider UIs.
Observing message arrival through documented and authorized APIs.
Reading message subjects and bodies.
Validating message content against expected values.
Measuring observed latency.
Measuring success, failure, and timeout rates.
Evaluating automation stability.
Producing benchmark reports and evidence.
Comparing providers using a documented methodology.

Explicitly exclude:

Implementing a production email delivery platform.
Building a public-facing SMTP service.
Bypassing provider security controls.
Using undocumented private APIs by default.
Circumventing CAPTCHA or access restrictions.
Treating unsupported API functionality as a provider delivery failure.
Making unsupported claims about the exact time a message reaches a provider's internal infrastructure.

The local SMTP server is the sending mechanism and a source of measurement timestamps. Acceptance by the local SMTP server does not establish successful delivery to the external provider.

7. Measurement Methodology

Define the following timestamp concepts:

SMTPACCEPTEDAT: The local SMTP server accepted the message for processing.
UIFIRSTDETECTED_AT: The message was first detected through the UI.
UICONTENTAVAILABLE_AT: The required subject and body became accessible through the UI.
APIFIRSTDETECTED_AT: The message was first identified through the API.
APICONTENTAVAILABLE_AT: The required content became accessible through the API.

Define these derived metrics:

UI detection latency = UIFIRSTDETECTEDAT minus SMTPACCEPTED_AT.
UI content latency = UICONTENTAVAILABLEAT minus SMTPACCEPTED_AT.
API detection latency = APIFIRSTDETECTEDAT minus SMTPACCEPTED_AT.
API content latency = APICONTENTAVAILABLEAT minus SMTPACCEPTED_AT.
UI content access duration = UICONTENTAVAILABLEAT minus UIFIRSTDETECTEDAT.
API content access duration = APICONTENTAVAILABLEAT minus APIFIRSTDETECTEDAT.

Explain that these measurements represent observed latency from local SMTP acceptance, not the provider's exact internal delivery time.

Account for:

Polling intervals.
Request durations.
Clock precision.
Timeouts.
Network delays.
Provider-specific behavior.
Differences between UI and API.
Differences in access and caching behavior.

Define a fair comparison methodology and identify circumstances where direct comparisons would be misleading.

16. Working Instructions

Do not write implementation code.

Do not claim to have verified provider capabilities unless evidence supports the claim.

If current provider documentation is needed, use official sources and cite them.

Clearly separate confirmed facts, assumptions, recommendations, and unresolved questions.

Avoid arbitrary scoring weights unless you justify them and explain how stakeholders can adjust them.

Do not force a single overall ranking if the evidence supports different winners for different use cases.

If essential business information is missing, ask focused clarification questions. Otherwise, state reasonable assumptions and proceed with a complete first draft.

The final result must be suitable for review and approval by a QA Manager before technical implementation begins.
